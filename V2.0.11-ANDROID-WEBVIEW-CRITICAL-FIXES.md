# v2.0.11 - Android WebView Critical Fixes (20 January 2026)

## 🎯 The Core Problem

**Android WebView's aggressive resource management** was killing the MediaStream during the recording flow, causing these symptoms:

- ✅ Mic check modal works (permission granted, stream active)
- ✅ User clicks "Sounds Good" (stream saved)
- ✅ Countdown shows (5... 4... 3... 2... 1...)
- ❌ Recording fails (MediaStreamTrack.readyState = 'ended' instead of 'live')

## 🔬 Root Cause Analysis

Android WebView treats MediaStream lifecycle differently than desktop/iOS browsers:

### Issue #1: AudioContext.close() Kills MediaStreamTrack
**Location**: [transcription-status.html:2422](public/transcription-status.html#L2422)

**Before (BROKEN):**
```javascript
function proceedWithRecording() {
    microphoneStream = micCheckStream; // ✅ Save stream

    if (micCheckContext) {
        micCheckContext.close(); // ❌ KILLS THE TRACK IN ANDROID!
    }
}
```

**Why it breaks**: When you call `AudioContext.close()` on a context that has a `MediaStreamSource` connected to a microphone track, Android WebView interprets this as "the app is done with the microphone" and marks the `MediaStreamTrack.readyState` as `'ended'`.

### Issue #2: Countdown Overlay Causes "Abandonment"
**Location**: [transcription-status.html:2433-2494](public/transcription-status.html#L2433-L2494)

**Before (BROKEN):**
```javascript
function showCountdown() {
    // Show full-screen overlay (z-index: 10001, rgba(0,0,0,0.9))
    overlay.classList.add('active');

    // Wait 5 seconds...
    // During this time, NO AudioContext is using the stream!

    // Android thinks: "Stream unused for 5 seconds = app doesn't need it anymore"
}
```

**Why it breaks**: Android WebView monitors MediaStream usage. If a stream isn't actively connected to an AudioContext for several seconds, Android may mark it as inactive as a battery/resource optimization.

### Issue #3: No Fallback Recovery
**Location**: [transcription-status.html:2519-2521](public/transcription-status.html#L2519-L2521)

**Before (BROKEN):**
```javascript
if (audioTracks[0].readyState !== 'live') {
    throw new Error('Microphone stream is not active'); // ❌ HARD FAIL
}
```

**Why it breaks**: No recovery mechanism. If the stream died, the app just crashes with an error message instead of attempting to re-request permission.

## ✅ Three-Part Solution

### Fix #1: Keep AudioContext Alive During Cleanup
**Changed**: [transcription-status.html:2404-2441](public/transcription-status.html#L2404-L2441)

```javascript
function proceedWithRecording() {
    microphoneStream = micCheckStream; // ✅ Save stream

    // CRITICAL FOR ANDROID WEBVIEW: Do NOT close the AudioContext!
    if (micCheckContext && micCheckAnalyser && micCheckContext.state === 'running') {
        try {
            // Disconnect nodes but keep context alive
            micCheckAnalyser.disconnect();
            console.log('🔇 Disconnected mic check audio nodes (context staying alive for Android)');
        } catch (e) {
            console.warn('Could not disconnect audio nodes:', e);
        }
    }
    // Note: We never call micCheckContext.close()!
}
```

**What it does**:
- Disconnects audio nodes to stop visualization
- Keeps AudioContext alive so Android knows we're still using the microphone
- Prevents MediaStreamTrack from being marked as 'ended'

### Fix #2: Keep-Alive AudioContext During Countdown
**Changed**: [transcription-status.html:2433-2495](public/transcription-status.html#L2433-L2495)

```javascript
function showCountdown() {
    return new Promise((resolve) => {
        // ANDROID WEBVIEW FIX: Keep the stream actively used during countdown
        let keepAliveContext = null;
        let keepAliveSource = null;

        if (microphoneStream) {
            try {
                // Create a minimal AudioContext to keep the stream alive
                keepAliveContext = new (window.AudioContext || window.webkitAudioContext)();
                keepAliveSource = keepAliveContext.createMediaStreamSource(microphoneStream);
                // Don't connect to destination - we just need it to exist
                console.log('🔊 Created keep-alive AudioContext during countdown');
            } catch (e) {
                console.warn('Could not create keep-alive context:', e);
            }
        }

        // ... countdown logic ...

        // Clean up keep-alive context after countdown
        if (keepAliveContext) {
            keepAliveContext.close();
            console.log('🔇 Closed keep-alive context after countdown');
        }
    });
}
```

**What it does**:
- Creates a "dummy" AudioContext during countdown
- Connects MediaStreamSource to keep stream "in use"
- Prevents Android from marking stream as abandoned
- Closes keep-alive context only AFTER countdown completes

### Fix #3: Fallback Recovery Mechanism
**Changed**: [transcription-status.html:2506-2545](public/transcription-status.html#L2506-L2545)

```javascript
async function startRecording() {
    let stream = microphoneStream;

    if (!stream) {
        throw new Error('Microphone stream not available');
    }

    const audioTracks = stream.getAudioTracks();
    console.log('🎤 Track states:', audioTracks.map(t => `${t.label}: ${t.readyState}`));

    // ANDROID WEBVIEW FALLBACK: If stream died, request microphone again
    if (audioTracks.length === 0 || audioTracks[0].readyState !== 'live') {
        console.warn('⚠️ Stream tracks are not live, attempting to request microphone again...');

        try {
            // Last resort: request microphone permission again
            stream = await navigator.mediaDevices.getUserMedia({
                audio: {
                    echoCancellation: true,
                    noiseSuppression: true,
                    autoGainControl: true
                }
            });

            microphoneStream = stream;
            console.log('✅ Successfully re-requested microphone access');

        } catch (fallbackError) {
            console.error('❌ Fallback microphone request failed:', fallbackError);
            throw new Error('Microphone stream became inactive and could not be reactivated');
        }
    }

    // ... continue with recording ...
}
```

**What it does**:
- Checks if MediaStreamTrack.readyState is 'live'
- If not, attempts to request getUserMedia() again
- Updates saved stream reference
- Provides graceful recovery instead of hard failure

## 📊 Technical Deep Dive

### Android WebView MediaStream Lifecycle

Android WebView tracks MediaStream usage through:

1. **AudioContext connections**: If a MediaStreamSource exists in a 'running' AudioContext
2. **MediaRecorder usage**: If a MediaRecorder is actively recording from the stream
3. **Time-based heuristics**: If stream unused for N seconds (appears to be ~3-5 seconds)

### Why Desktop/iOS Browsers Don't Have This Issue

- **Desktop Chrome/Firefox**: More permissive MediaStream lifecycle management
- **iOS Safari/WebView**: Different security model, less aggressive resource cleanup
- **Android Browser**: Works differently than Android WebView (less strict)

### The "Keep-Alive" Pattern

This is a known pattern for Android WebView development:

```javascript
// Pattern: Keep stream "in use" during idle periods
let keepAliveContext = new AudioContext();
let keepAliveSource = keepAliveContext.createMediaStreamSource(stream);
// Don't connect to destination - just need the connection to exist
// This signals to Android: "We're still using this stream!"
```

## 📝 Key Learnings

1. **Android WebView ≠ Android Browser** - WebView is more restrictive
2. **AudioContext lifecycle matters** - closing it signals "done with audio"
3. **MediaStream needs active use** - idle streams get killed
4. **Keep-alive pattern is essential** - maintain connection during idle periods
5. **Always have fallback** - graceful recovery beats hard failures
